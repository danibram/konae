Edit the app's files with the CLI

Log in, create a folder with init, run it locally with dev, and send it to the Kernel with publish.

Before you start

You need a Littlebox installation to talk to, and an account on it. login reads LITTLEBOX_EMAIL and LITTLEBOX_PASSWORD. To create the account in the same step, also set LITTLEBOX_INVITATION_CODE, the code the operator issued, or LITTLEBOX_SETUP_KEY for the installation's first owner. The commands below run from a checkout of the repository.

Steps

  1. Log in. This saves a 24-hour token with read, write and publish in <folder>/.littlebox/credentials.json. Keep .littlebox out of Git. LITTLEBOX_MCP_TOKEN overrides the file. 
    LITTLEBOX_EMAIL=you@example.com LITTLEBOX_PASSWORD=... \
bun run littlebox -- login --dir /tmp/my-app --url http://localhost:4173
  2. Create the project. init needs an empty folder. It registers the project on the Kernel and writes the template and a littlebox.json. It writes the app private, with signup policy Invitation only. 
    bun run littlebox -- init --dir /tmp/my-app --name 'My app' --url http://localhost:4173
  3. Run it locally. dev starts a Development Kernel with its own identities, data and files under .littlebox/dev-data, and republishes each time you save a file. It publishes locally as Open so test accounts can sign up, and it never proxies production. The default port is 8796. 
    bun run littlebox -- dev --dir /tmp/my-app
  4. Edit the Capsule files in the folder. Open the URL dev prints and reload after each change. Email, notices included, goes to .littlebox/dev-data/mailbox.jsonl.
  5. Optional. Write the Action Contract and, against a test Deployment, check every action's answers. 
    bun run littlebox -- contract --dir /tmp/my-app
bun run littlebox -- conform --url <app URL> --contract /tmp/my-app/action-contract.json
    conform runs each mutation once, so point it at a test Deployment.
  6. Publish. This builds the folder and publishes it with the credential from login. It prints the Deployment URL. 
    bun run littlebox -- publish --dir /tmp/my-app
  7. Open the Deployment URL and call one Server Action.

Visibility and signup

publish deploys the app as private unless littlebox.json sets project.manifest.visibility to "public". project.manifest.signupPolicy names who may create an app account on the first release. A later publish that names another policy warns and changes nothing. Change it in the editor's Auth > Users view or with signup_policy_set.

Check it worked

Do not treat the URL publish printed as proof. Read the Deployment back through MCP, the same door the CLI wrote through.

  • The read-back for release_apply is project_inspect. It shows the live Deployment and its URL.
  • The read-back for project_create is project_inspect as well.
  • Open the Deployment URL, then call one Server Action. actions_invoke is its own read-back, so call a query to see a row you wrote.
  • Decide what your credential may do from session_inspect's can map, not from memory of which flag login took.

What differs from the editor preview

dev runs the same Rust Kernel as a Deployment, so HTTP routes, the schedule timer, notice email, Usage and the call outbox all work there. The editor preview has none of them. The Validation Gate checks the schema and actions.json only, so a page that names a missing file fails at build or publish.
