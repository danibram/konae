Littlebox overview

Littlebox lets a person who does not write code, and a person who does, make the same small app and take it to another machine with its accounts, its data and its rules unchanged.

The code, who may open a Deployment, and who may read a row stay separate. The Validation Gate in the editor and the Kernel that serves the app refuse the same Capsule with the same words. A check that passes in the editor still passes on the machine the app leaves on.

The five jobs

  1. A person who does not write code describes an app and gets one that runs.
  2. A person who writes code edits the same app's files.
  3. Both of them hit the same checks. A query that reads rows names a LIMIT, in the editor and on the Kernel that leaves with the app.
  4. Either person can take the app to another machine with its accounts, its data and its rules.
  5. Who may open the app, and who may read a row, stay decisions of the app. The host does not replace them.

How to decide what belongs

A new capability belongs in the product only when the Validation Gate and the Kernel refuse it with the same words, and a package can carry the app's accounts, data and rules. Anything else is operator work on the installation, not an App feature.

After any write through MCP or the editor, observe the effect through the same door before retrying or telling the owner it worked. The rules topic of platform_guide lists the read-back for each write tool. Decide what a credential may do from the can map of session_inspect, not from memory of login flags.

Start here

These are the three steps of a first run. Run the commands from the Littlebox repository root.

1. Get a credential

bun run littlebox -- login --dir ./my-app --url http://localhost:4173

login reads LITTLEBOX_EMAIL and LITTLEBOX_PASSWORD from the environment and saves a 24-hour token with read, write and publish in ./my-app/.littlebox/credentials.json. The CLI reference lists the other variables and flags.

2. Get an app that runs

bun run littlebox -- init --dir ./my-app --name 'My app' --url http://localhost:4173
bun run littlebox -- dev --dir ./my-app

init registers the project and writes a template. dev runs the app on a local Development Kernel and republishes when the files change. To publish to the Kernel the credential names, run bun run littlebox -- publish --dir ./my-app.

In the editor, the same step is an apply through the Validation Gate. The first app guide walks through it.

3. Prove it

  • Open the Deployment URL.
  • Call one Server Action from the page.
  • Read the project back with project_inspect over MCP.
  • When you are checking a contract, run conform against action-contract.json.

If this path grows, the product got harder. The fix is to shorten the path, not to add a page.

For agents

An agent that connects over MCP calls platform_describe and projects_list first. It then reads the rules and pieces topics of platform_guide. The MCP reference lists every topic. This site publishes llms.txt with a link to each page's source fragment.
