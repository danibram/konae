# Build and ship StarlingMonkey functions

The editor and the CLI both publish self-contained ESM for each declared function. The destination Kernel prepares StarlingMonkey components before a released version can serve. The preferred layout is one component per version. A person can copy the published app folder to a matching Kernel and sign in with the same app account. Server Actions keep the same row rules. [ADR 0020](../adr/0020-wasm-functions-runner.md) records the proposed decision.

## 1. Componentize at the destination before serving

Use a Rust helper with the ComponentizeJS 0.21.0 splicer, the pinned StarlingMonkey engine, Wizer and `wit-component`. Package it with the Kernel and keep it out of the HTTP request path. The Kernel invokes it on a bounded blocking build queue during release preparation, source import, and startup when loading an exported folder or replacing an incompatible cache. A release plan can prepare a candidate early. Apply rechecks the source revision and exact artifact digest before it pins the prepared result. Run the same local step in `konae dev`; keep `konae build`'s output usable by either door.

The helper takes the sorted names and self-contained bundles already checked by the existing server artifact validator. For the one-component layout, it generates an entry that imports each bundle as a separate module and selects its handler by the name in Invoke. A worker uses a fresh Store for each invocation. Package the adapter, WIT and reactor adapter with the helper. Pass only generated binding metadata and staged source inputs to Wizer. The builder runs top-level JS, so give its subprocess a separate identity, an isolated scratch directory, no installation environment or app data, and a deadline and memory limits. Allow only the WASI operations needed to read staged inputs, write bounded diagnostics and initialize deterministically. Seal the snapshot before precompiling. Link only the four typed calls in `konae:worker/host`: action call, body read, failure and the runtime clock. The clock and action capabilities become available only during invocation, as allowed by the existing contract.

The browser's `src/runtime/browser-build.ts` and `src/kernel/functions.ts` already emit the ESM envelope. Adding Node and ComponentizeJS to both Kernel images would put npm and a second runtime in the destination's trusted toolchain. Componentizing separately in `konae build` would duplicate the build gate and require the editor installation to ship the tool anyway. The Rust helper costs a pinned splicer dependency and seconds of preparation per changed artifact. Wizer still runs in a subprocess because it executes app initialization and must be killable even if it stops making progress. ComponentizeJS's release contains engine-specific binding edits and WASI stubbing. Wizer and `wit-component` alone cannot replace those steps. [ComponentizeJS 0.21.0](https://github.com/bytecodealliance/ComponentizeJS/tree/0.21.0)

## 2. Carry the published ESM

Keep `server/manifest.json` at `konae-functions/1`, with SHA-256 over each published `server/<name>.mjs`. Carry the released manifest, bundle bytes and snapshot of effective settings with the folder. Verify the names and hashes against the release metadata, using the published files even when `app/` has drafts ahead. The local component ABI is `konae-functions-wasm/1`. It is independent of the folder ABI and IPC/3. The installation holds the portable component and its verified digest while preparing native code. The folder and package accept only their declared ESM files.

A portable Wasm file and an author-supplied hash could prove the bytes survived a transfer. They could not bind the behavior of those bytes to the published ESM. Accepting both as peers would need a second trust mechanism or a destination rebuild. Carrying Wasm would also grow each export by the size of an engine snapshot. A 19,930,258-byte component would occupy 26,573,680 bytes in base64, more than the current 26,000,000-byte release JSON cap before any other fields. A binary transfer would avoid base64 and would still need a separate trust decision. Keeping ESM uses the existing 1 MiB per bundle and 8 MiB total caps. The cost is a first preparation on a new installation, including standalone Kernel startup; an export does not need npm or network access to start.

Prepare using the exact bytes destined for the existing staged `server/` directory. `deployments/release.rs` validates and stages the server artifact before `switch_dist` swaps `dist/` and `server/`. Use the same preparation for folder startup, package import and the backup restore in `app_folders/import.rs`. A Kernel without a configured function runner keeps its existing function-unavailable behavior. Build outside the database lock and before any live swap. Recheck the release reference under the existing lock, pin the new cache entry through the swap, and leave the old deployment available if preparation fails. A data-only `konae push` or `konae pull --data-only` needs no function build. A full pull carries the existing published files. Source replacement prepares the incoming release, and an export or import leaves the installation cache behind.

## 3. Give both doors the same refusal

Keep the portable checks offline in the Gate and Kernel. The Gate can check the ESM contract, normalized manifest and bundle hashes without a connection. For a function-bearing change, online Apply calls a read-only owner check on the candidate ESM and relays the very same native preparation result as publish, import and startup. Use the owner transfer mechanism for bounded bytes and the project's `write` permission, including project scope. Tie the check result to the scratch revision and build fingerprint. If disconnected, show the engine check as pending and keep that proposal pending. A purely offline JS parse cannot decide whether Wizer will finish. Direct CLI publish runs the same preparation through the Kernel even if the caller skipped the editor.

Read `kernel-rs/kernel/src/functions-cases.json` and `functions-artifact-cases.json`, consumed by `functions/manifest_artifact.rs` and the TS tests. Keep `function.bundle-contract` with its existing words, "Function {name} bundle must be a self-contained ESM module exporting handle." It covers source imports and a missing named ESM export. The following codes and cases are new. Register the code and remedy in `kernel-rs/kernel/src/refusal-codes.json`. Share fixtures in `functions-artifact-cases.json` for the new metadata checks and in `functions-wasm-cases.json` for the helper's component and initialization checks. Use generated components for import and export fixtures. The Gate tests the actual check response and its rendering; Rust tests the helper that emits it.

| Code | Exact message | Case |
| --- | --- | --- |
| `function.artifact-digest` | Server Artifact hashes do not match its bundles. | Existing folder check gains a code. Flip a bundle byte. |
| `function.wasm-abi` | The function component requires ABI konae-functions-wasm/1. | Wrong or absent component ABI. |
| `function.wasm-digest` | The function component SHA-256 does not match its manifest. | Change a component byte after the helper reports its digest. |
| `function.wasm-import` | The function component has an import outside the allowed host interface. | Extra import, WASI import or incompatible host function type. |
| `function.wasm-export` | The function component is missing a required export or its type does not match. | Missing or wrong typed runner export. Also check that each named ESM `handle` is callable during preparation. |
| `function.wasm-api` | A function uses an API that StarlingMonkey does not support. | An unsupported API evaluated during build, such as WebAssembly. |
| `function.wasm-init-pending` | A function must finish its top-level initialization before it can run. | Top-level await on an unsettled promise. |
| `function.wasm-init-effect` | A function cannot start timers or fetch during top-level initialization. | One fixture for a timer and one for fetch, including calls the bundle catches. |
| `function.wasm-init` | A function failed during top-level initialization. | An ordinary throw during evaluation. |
| `function.wasm-build-limit` | Function component preparation exceeded its build limits. | Infinite initialization or a build over its resource limit. |
| `function.wasm-invalid` | The function component is not valid WebAssembly. | Truncated or malformed output with a matching digest. |

Validate component encoding and ABI, digest, then typed imports and exports before native compilation. Treat an invalid stored local entry as a cache miss and regenerate before serving. Treat an invalid fresh output as a preparation refusal. Use a typed helper status for API and initialization failures, with bounded diagnostics as a separate field. Never depend on SpiderMonkey's English exception text. A snapshot check must observe module evaluation completing and its initialization jobs settling. ComponentizeJS 0.21.0 emitted a 12,519,928-byte component for `await new Promise(() => {})` after the exported functions. Engine success alone therefore cannot discharge this check. Add a typed preparation check that can observe the end of each module evaluation, then test it against a pending and a resolved top-level await. A standalone Promise that queues no work and does not hold up module evaluation differs from an unfinished top-level await. For timers and fetch, record the attempt even if the JS catches the rejection. Keep invocation-time API refusals under the runtime contract. Helper absence, queue saturation and cache I/O failures identify an operator issue. They must never look like a refusal of the Capsule.

## 4. Budget native storage and resident memory

Key the native object by (component digest, engine digest, Wasmtime version, target). Include CPU features and Wasmtime configuration in target compatibility. Map the ordered bundle names and SHA-256 hashes, WIT ABI and complete builder fingerprint to the prepared component digest. Build once per missing key. Publish cache entries by atomic rename after validation and file sync. Keep the native cache under the installation's private directory, outside the app tree. Give the worker a read-only handle to the exact checked object. Check regular-file type and ownership at open and reject writable or substituted files. Native deserialization trusts the local compiler and protected cache. A file or digest from an app folder cannot authorize deserialization.

Budget approximately 50 to 58 MB per distinct prepared version from the spike's native files. Four distinct versions with two slots each use about 200 to 232 MB. Eight distinct versions with one slot each use about 400 to 464 MB. Both are derived examples. Versions with zero live workers still need disk if published, so reserve about `58 MB × N` for `N` similarly sized distinct current versions, plus staged and draining versions. Keep space for a new object while the old one is pinned. A byte budget must meter actual file sizes and staging reservations. Refuse preparation before a flip if current entries and the staging reservation exceed it. Use actual bytes rather than treating the measured component as a maximum.

Using the supplied planning range of 8.7 to 17.6 MiB per worker, two slots cost about 17 to 35 MiB per Deployment and eight cost about 70 to 141 MiB summed worker RSS. The spike's orders reading was 8,672 KiB after Ready and 17,632 KiB after the warm run. Those are about 8.5 and 17.2 MiB. RSS counts shared pages in each worker and excludes build peaks, Kernel memory and other request peaks. Eight workers at the 256 MiB polling threshold sum to 2 GiB. Polling can overshoot between samples.

Pin a native object while a release plan can apply it, while a current app references it, or while a worker can still use it. Release old-version pins when both the deployment reference and last worker lease end. Reclaim unpinned entries oldest first when reserving space, expire unused plan pins with their plans, and sweep obsolete build and target keys at startup after reconciling current references. Backups carry ESM and rebuild if restored. Worker eviction keeps today's per-app and global slot policy and never compiles on admission. A worker slot limit bounds RSS and cannot bound the number of published versions on disk.

## 5. Choose containment before the worker starts

Use an operator setting `KONAE_FUNCTIONS_RUNNER_KIND=wasm` for the new policy. Default to the existing deno policy when unset. Validate the configured, operator-installed binary and reject an unknown kind at startup. Add an engine kind to IPC/3 Ready and verify it against the selected policy before Invoke. Ready alone comes too late to choose launch policy. Probing would add another executable invocation and still require a check at Ready. The flag costs one setting for manual installations. Pin the packaged executable; the owner and app folder cannot choose the launcher.

Inside a Linux container, use a separate non-root UID and GID for Wasm workers. Clear groups, ambient capabilities, environment and inherited file descriptors, and set no-new-privileges. Arm parent-death handling after the identity change and retain process-group kill and reap on deadline or RSS excess. Use Wasmtime Store and allocation limits, epoch interruption and bounded IPC. Use hard rlimits for core dumps, descriptors and file growth, plus a finite address-space ceiling sized against the actual Wasmtime mapping plan. A low address-space limit can reject valid reserved guard pages. Treat a failed identity change, missing RSS observation for a live worker or failed limit setup as a launch failure. Never silently enter development policy. Keep the container's default seccomp and AppArmor. Exercise executable mappings, threads, RSS and cross-UID termination in CI before shipping.

The existing `runtime.rs` ties separate identity to `MemoryPolicy::LinuxCgroup`; add a distinct Wasm policy in the executor. Split out the identity and process setup from cgroup attachment. The deno-specific `sandbox.rs` policy still applies to deno. The Wasm guest has no WASI file, network, process or ambient time imports. Keep the worker and helper away from app files and secrets via UID and file permissions, and expose only the needed cache file or staged input. Same-UID development remains explicit and loopback-only.

For a new Wasm export, generated `.env.example` and Compose name the packaged runner, Wasm kind and worker UID/GID. Keep the named installation volume for the cache. The entrypoint prepares permissions then drops to the Kernel UID, preserving only the capabilities needed to switch the worker identity and kill it (`SETUID`, `SETGID`, `KILL` within the container). Use Docker's default profiles and namespace. The Wasm path performs no cgroup mount or delegation and needs no `SYS_ADMIN` or AppArmor override. Retain strict deno launch for an explicitly configured deno installation and the original service shape for an export without functions.

The [spike report](functions-wasm-spike.md) exercised Linux userspace under Docker's VM kernel with UID 65534 and zero worker capabilities. It disabled the container seccomp profile for those probes. It did not establish the proposed launch policy on a stock kernel with default profiles. Prove that on Ubuntu 24.04 with an exported app, an empty cache, authenticated GET and POST through the Kernel, separate worker IDs, zero worker capabilities, default security profiles and no delegated cgroup. Verify deadline and RSS kills and that a stopped child releases its slot. Retain the deno launch coverage.

## Production acceptance

Warm ratios divide StarlingMonkey's time by the matching baseline. The guard is 1.5× or less. Cold passes if StarlingMonkey's maximum is under 250 ms. The snapshot rows decide the production verdict.

Pair StarlingMonkey with deno_core with snapshot on warm GET, warm POST and the slowest repeated Hono case, following the [spike's methodology](functions-wasm-spike.md#final-verdict). Measure cold after preparation. Report preparation separately, including an empty cache, so the HTTP cold limit cannot hide a cache-miss build. Check IPC/3, large request bodies, UTF-8 response bounds, multipart bytes, `Response.clone`, cancellation and shutdown before release.
