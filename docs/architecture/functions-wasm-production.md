# Build and ship StarlingMonkey functions

The editor and the CLI both publish self-contained ESM for each declared function. The two builders can emit different bytes for the same dependency because one reads esm.sh and the other reads installed packages. Preparation always uses the bytes the caller publishes. The destination Kernel prepares StarlingMonkey components before a released version can serve. The preferred layout is one component per version. A person can copy the published app folder to a matching Kernel and sign in with the same app account. Server Actions keep the same row rules. [ADR 0020](../adr/0020-wasm-functions-runner.md) records the proposed decision.

## 1. Componentize at the destination before serving

Use a Rust helper with the ComponentizeJS 0.21.0 splicer, the pinned StarlingMonkey engine, Wizer and `wit-component`. Package it with the Kernel and keep it out of the HTTP request path. The Kernel invokes it on a bounded blocking build queue during release preparation, source import, and startup when loading an exported folder or replacing an incompatible cache. A release plan can prepare a candidate early. Apply rechecks the source revision and exact artifact digest before it pins the prepared result. Run the same local step in `konae dev`; keep `konae build`'s output usable by either door.

The helper takes the sorted names and self-contained bundles already checked by the existing server artifact validator. For the one-component layout, it generates an entry that imports each bundle as a separate module and selects its handler by the name in Invoke. A worker uses a fresh Store for each invocation. Package the adapter, WIT and reactor adapter with the helper. Pass only generated binding metadata and staged source inputs to Wizer. The builder runs top-level JS, so give its subprocess a separate identity, an isolated scratch directory, no installation environment or app data, a deadline and memory limits. Allow only the WASI operations needed to read staged inputs, write bounded diagnostics and initialize deterministically. Seal the snapshot before precompiling. Link only the four typed calls in `konae:worker/host`: action call, body read, failure and the runtime clock. Preparation gets a fixed clock and no action capabilities. The running guest gets the clock and per-request capabilities defined by the runtime contract.

The browser's `src/runtime/browser-build.ts` and `src/kernel/functions.ts` already emit the ESM envelope. Adding Node and ComponentizeJS to both Kernel images would put npm and a second runtime in the destination's trusted toolchain. Componentizing separately in `konae build` would duplicate the build gate and require the editor installation to ship the tool anyway. The Rust helper costs a pinned splicer dependency and seconds of preparation per changed artifact. Wizer still runs in a subprocess because it executes app initialization and must be killable even if it stops making progress. ComponentizeJS's release contains engine-specific binding edits and WASI stubbing. Wizer and `wit-component` alone cannot replace those steps. [ComponentizeJS 0.21.0](https://github.com/bytecodealliance/ComponentizeJS/tree/0.21.0)

### Component build experiment

On an Apple M3 Pro running macOS arm64, I copied the spike's `hello`, `count` and Hono `orders` bundles. I used esbuild 0.25.12 once to assemble each input with the same guest adapter. Both build paths then read the same assembled ESM and `guest/starling.wit`. Each cell is the range of two fresh processes with reversed order on the second round. Wall time includes process startup and writing the portable bytes. It excludes ESM assembly and native precompilation. Host one-minute load during the comparison was 24 to 35.

| Input | Node 26.0.0 and ComponentizeJS 0.21.0 | Rust 1.91.0 |
| --- | ---: | ---: |
| Hello, 4,898 input bytes | 2.37 to 2.62 s, 12,518,253 to 12,518,261 bytes | 9.24 to 10.72 s, 12,518,179 to 12,518,203 bytes |
| Hello, count and orders, 819,454 input bytes | 2.45 to 4.12 s, 19,930,216 to 19,930,244 bytes | 8.05 to 11.53 s, 19,930,214 to 19,930,257 bytes |

The Rust driver called `splice_bindings` from the 0.21.0 tag against engine SHA-256 `b45eb4dda2fed0eaecd4e5581fb26a99e642d001dbf82f3698aba27564a78ea1`. It staged the generated initializer and source, executed the Wizer 10.0.0 Rust binary with only the generated environment, called `check_init` with Wasmtime 38.0.4, and then stubbed WASI. It encoded with `wit-component` 0.245.1 and Jco 1.42.0's reactor adapter. The first run reached encoding and failed when `ComponentEncoder` tried to merge `wasi:sockets/network@0.2.10` and `@0.2.12`. Disabling semver import merging fixed it. Keep validation and require exact typed imports after encoding. The splicer and Wizer took 0.70 to 1.84 s together in the combined runs. The remaining time includes the separate Wasmtime initialization check. The production helper can avoid recompiling the core solely to check initialization if it can check completion in the snapshot process.

The same Rust driver accepted a directory of three separate ESM modules and a prebundled adapter in 11.42 s. This test did not need Node for build-time module assembly. It produced 19,924,326 portable bytes. The combined-input Rust artifact compiled into 57,712,384 native bytes in 9.57 s locally. A smoke host supplied fixture action responses and invoked each function in a fresh Store. The replies were `200 wasm-ok`, `200 {"n":1}`, and `200 {"id":1,"ownerId":"alice","quantity":2}`. The corresponding three separate spike artifacts total 44,980,753 portable bytes and 157,424,560 macOS native bytes.

I also built separate hello and count components from the exported app's ESM, cross-compiled them with Wasmtime 38.0.4, and ran `measure/run-export.sh` with the archived Linux IPC/2 Kernel and runner. In the Debian 12 container on Docker Desktop's Linux 7.0.14 arm64 VM, an authenticated `GET /api/hello` returned 200 and `wasm-ok`. An authenticated `POST /api/count` with `{"amount":1}` returned 200 and `{"n":20}` from a starting count of 19. Thirty more requests reached `{"n":50}`. The container used UID 65534, zero capabilities, default seccomp, no network and a read-only native cache. This proves execution of the Rust-built snapshots on Linux. The lab Kernel used development mode. The production IPC/3 launch policy and separate worker identity still need the stock-kernel check below.

### Keep each function's JavaScript globals private

The combined trial used one realm. When function A set a global during initialization, function B returned `1` on its first call. B returned `0` when built alone. A fresh Store resets invocation state, but it brings back the same shared globals captured by Wizer. The current runner evaluates only the named bundle, so this changes what a function can see.

Use per-bundle snapshots in the first production implementation. Pin their keys as one app version, and let IPC/3 select the prepared component by name. Load only the selected compiled object when a request needs it. Keep the folder identical for both layouts. This costs more preparation time and disk. Reuse prepared entries for unchanged bundles.

One component with a separate realm for each bundle remains the preferred optimization. Spend at most one day checking whether the pinned embedding can create and snapshot separate realms. Run two bundles where A changes a global and a prototype at initialization and invocation. B must see neither change. Repeat A to check that its request changes reset, and check that each function calls only its declared actions. Compare both layouts with the warm and cold guard below. Keep per-bundle snapshots if separate realms need engine work or miss the guard.

## 2. Carry the published ESM

Keep `server/manifest.json` at `konae-functions/1`, with SHA-256 over each published `server/<name>.mjs`. Carry the released manifest, bundle bytes and snapshot of effective settings with the folder. Verify the names and hashes against the release metadata, using the published files even when `app/` has drafts ahead. The local component ABI is `konae-functions-wasm/1`. It is independent of the folder ABI and IPC/3. The helper returns a bounded portable component and a manifest with ABI, component digest and the ordered input digest. Validate and precompile that same buffer. Keep the digest in the local preparation record and discard the portable bytes after native compilation. The folder and package accept only their declared ESM files.

A portable Wasm file and an author-supplied hash could prove the bytes survived a transfer. They could not bind the behavior of those bytes to the published ESM. Accepting both as peers would need a second trust mechanism or a destination rebuild. Carrying Wasm would also grow each export by the size of an engine snapshot. A 19,930,258-byte component would occupy 26,573,680 bytes in base64, more than the current 26,000,000-byte release JSON cap before any other fields. A binary transfer would avoid base64 and would still need a separate trust decision. Keeping ESM uses the existing 1 MiB per bundle and 8 MiB total caps. The cost is a first preparation on a new installation, including standalone Kernel startup; an export does not need npm or network access to start.

Prepare using the exact bytes destined for the existing staged `server/` directory. `deployments/release.rs` validates and stages the server artifact before `switch_dist` swaps `dist/` and `server/`. Use the same preparation for folder startup, package import and the backup restore in `app_folders/import.rs`. An explicitly configured deno installation skips Wasm preparation. A Kernel without a runner keeps its existing function-unavailable behavior. Authorize and validate input first. Build before acquiring release and database locks and before any live swap. Recheck the release reference under the existing lock, pin the new cache entry through the swap, and leave the old deployment available if preparation fails. A data-only `konae push` or `konae pull --data-only` needs no function build. A full pull carries the existing published files. Source replacement prepares the incoming release, and an export or import leaves the installation cache behind.

## 3. Give both doors the same refusal

Keep the portable checks offline in the Gate and Kernel. The Gate can check the ESM contract, normalized manifest and bundle hashes without a connection. For a function-bearing change, online `validate_capsule` and Apply call a read-only owner check on the candidate ESM. They relay the native preparation result that publish, import and startup use. Use the owner transfer mechanism for bounded bytes and the project's `write` permission, including project scope. Tie the check result to the scratch revision and build fingerprint. If disconnected, show the engine check as pending and keep that proposal pending. A purely offline JS parse cannot decide whether Wizer will finish. Direct CLI publish runs the same preparation through the Kernel even if the caller skipped the editor.

Read `kernel-rs/kernel/src/functions-cases.json` and `functions-artifact-cases.json`, consumed by `functions/manifest_artifact.rs` and the TS tests. Keep `function.bundle-contract` with its existing words, "Function {name} bundle must be a self-contained ESM module exporting handle." It covers source imports and a missing named ESM export. Preparation uses it for a named ESM `handle` that is present but cannot be called. The following codes and cases are new. Register the code and remedy in `kernel-rs/kernel/src/refusal-codes.json`. Share fixtures in `functions-artifact-cases.json` for the new metadata checks and in `functions-wasm-cases.json` for the helper's component and initialization checks. Use generated components for import and export fixtures. The Gate tests the actual check response and its rendering; Rust tests the helper that emits it.

| Code | Exact message | Case |
| --- | --- | --- |
| `function.artifact-digest` | Server Artifact hashes do not match its bundles. | Existing folder check gains a code. Flip a bundle byte. |
| `function.wasm-abi` | The function component requires ABI konae-functions-wasm/1. | Wrong or absent component ABI. |
| `function.wasm-digest` | The function component SHA-256 does not match its manifest. | Change a component byte after the helper reports its digest. |
| `function.wasm-import` | The function component has an import outside the allowed host interface. | Extra import, WASI import or incompatible host function type. |
| `function.wasm-export` | The function component must export the required runner interface with matching types. | Missing, extra or incompatible runner export. |
| `function.wasm-api` | A function uses an API that StarlingMonkey does not support. | An unsupported API evaluated during build, such as WebAssembly. |
| `function.wasm-init-pending` | A function must finish its top-level initialization before it can run. | Top-level await on an unsettled promise. |
| `function.wasm-init-effect` | A function cannot start timers or fetch during top-level initialization. | One fixture for a timer and one for fetch, including calls the bundle catches. |
| `function.wasm-init` | A function failed during top-level initialization. | An ordinary throw during evaluation. |
| `function.wasm-build-limit` | Function component preparation exceeded its build limits. | Infinite initialization or a build over its resource limit. |
| `function.wasm-invalid` | The function component is not valid WebAssembly. | Truncated or malformed output with a matching digest. |

Check the component ABI, digest, encoding, typed imports and typed exports in that order before native compilation. Invalid fresh Wasm output points to the helper or its packaging, so component ABI, digest, encoding, import and export refusals carry an operator remedy. ESM contract and initialization refusals carry a Capsule remedy. Treat an invalid stored local entry as a cache miss and regenerate before serving. Treat an invalid fresh output as a preparation refusal. Use a typed helper status for API and initialization failures, with bounded diagnostics as a separate field. Never depend on SpiderMonkey's English exception text. A snapshot check must observe module evaluation completing and its initialization jobs settling. ComponentizeJS 0.21.0 emitted a 12,519,928-byte component for `await new Promise(() => {})` after the exported functions. Engine success alone therefore cannot discharge this check. The Rust probe called a typed snapshot export that reads a trusted end-of-module marker. It returned false for the pending await and true for a resolved await. Use that result with the completion check for initialization jobs. A standalone Promise that queues no work and does not hold up module evaluation differs from an unfinished top-level await. For timers and fetch, record the attempt even if the JS catches the rejection. Keep invocation-time API refusals under the runtime contract. Helper absence, queue saturation and cache I/O failures identify an operator issue. They must never look like a refusal of the Capsule.

## 4. Budget native storage and resident memory

Key the native object by (component digest, engine digest, Wasmtime version, target). Include CPU features and Wasmtime configuration in target compatibility. Map the ordered bundle names and SHA-256 hashes, WIT ABI and complete builder fingerprint to the prepared component digest. Build once per missing key. Share a pending build by key and tie its result to the exact input digest. Publish cache entries by atomic rename after validation and file sync. Keep the native cache under the installation's private directory, outside the app tree. Give the worker a read-only handle to the exact checked object. Check regular-file type and ownership at open and reject writable or substituted files. Native deserialization trusts the local compiler and protected cache. A file or digest from an app folder cannot authorize deserialization.

Budget approximately 50 to 58 MB per distinct prepared version from the spike's native files. Where there is one object per version, four distinct versions with two slots each use about 200 to 232 MB. Eight distinct versions with one slot each use about 400 to 464 MB. Both are derived examples. With separate snapshots, budget by distinct bundles. A three-bundle version like the spike set would use about 157 MB. Versions with zero live workers still need disk if published, so reserve about `58 MB × N` for `N` similarly sized distinct current components, plus staged and draining components. Keep space for a new object while the old one is pinned. A byte budget must meter actual file sizes and staging reservations. Refuse preparation before a flip if current entries and the staging reservation exceed it. Use actual bytes rather than treating the measured component as a maximum.

Using the supplied planning range of 8.7 to 17.6 MiB per worker, two slots cost about 17 to 35 MiB per Deployment and eight cost about 70 to 141 MiB summed worker RSS. The spike's orders reading was 8,672 KiB after Ready and 17,632 KiB after the warm run. Those are about 8.5 and 17.2 MiB. RSS counts shared pages in each worker and excludes build peaks, Kernel memory and other request peaks. Eight workers at the 256 MiB polling threshold sum to 2 GiB. With per-bundle snapshots, that worker budget assumes each worker keeps only the selected component resident. Polling can overshoot between samples.

Pin a native object while a release plan can apply it, while a current app references it, or while a worker can still use it. Release old-version pins when both the deployment reference and last worker lease end. Reclaim unpinned entries oldest first when reserving space, expire unused plan pins with their plans, and sweep obsolete build and target keys at startup after reconciling current references. Backups carry ESM and rebuild if restored. Worker eviction keeps today's per-app and global slot policy and never compiles on admission. A worker slot limit bounds RSS. Evicting current objects with no workers would force a later cold load to wait for compilation. Retaining every retired version would grow the cache after each publish.

## 5. Choose containment before the worker starts

Use an operator setting `KONAE_FUNCTIONS_RUNNER_KIND=wasm` for the new policy. Default to the existing deno policy when unset. Validate the configured, operator-installed binary and reject an unknown kind at startup. Add an engine kind to IPC/3 Ready and verify it against the selected policy before Invoke. Ready alone comes too late to choose launch policy. Probing would add another executable invocation and still require a check at Ready. The flag costs one setting for manual installations. Pin the packaged executable; the owner and app folder cannot choose the launcher.

Inside a Linux container, use a separate non-root UID and GID for Wasm workers. Clear groups, ambient capabilities, environment and inherited file descriptors, and set no-new-privileges. Arm parent-death handling after the identity change and retain process-group kill and reap on deadline or RSS excess. Use Wasmtime Store and allocation limits, epoch interruption and bounded IPC. Use hard rlimits for core dumps, descriptors and file growth, plus a finite address-space ceiling sized against the actual Wasmtime mapping plan. A low address-space limit can reject valid reserved guard pages. Treat a failed identity change, missing RSS observation for a live worker or failed limit setup as a launch failure. Never silently enter development policy. Keep the container's default seccomp and AppArmor. Exercise executable mappings, threads, RSS and cross-UID termination in CI before shipping.

The existing `runtime.rs` ties separate identity to `MemoryPolicy::LinuxCgroup`; add a distinct Wasm policy in the executor. Split out the identity and process setup from cgroup attachment. The deno-specific `sandbox.rs` policy still applies to deno. The Wasm guest has no WASI file, network, process or ambient time imports. Keep the worker and helper away from app files and secrets via UID and file permissions, and expose only the needed cache file or staged input. Same-UID development remains explicit and loopback-only.

For a new Wasm export, generated `.env.example` and Compose name the packaged runner, Wasm kind and worker UID/GID. Keep the named installation volume for the cache. The entrypoint prepares permissions then drops to the Kernel UID, preserving only the capabilities needed to switch the worker identity and kill it (`SETUID`, `SETGID`, `KILL` within the container). Use Docker's default profiles and namespace. The Wasm path performs no cgroup mount or delegation and needs no `SYS_ADMIN` or AppArmor override. Retain strict deno launch for an explicitly configured deno installation and the original service shape for an export without functions.

The [spike report](functions-wasm-spike.md) exercised Linux userspace under Docker's VM kernel with UID 65534 and zero worker capabilities. It disabled the container seccomp profile for those probes. It did not establish the proposed launch policy on a stock kernel with default profiles. Prove that on Ubuntu 24.04 with an exported app, an empty cache, authenticated GET and POST through the Kernel, separate worker IDs, zero worker capabilities, default security profiles and no delegated cgroup. Verify deadline and RSS kills and that a stopped child releases its slot. Retain the deno launch coverage.

## Production acceptance

Warm ratios divide StarlingMonkey's time by the matching baseline. The guard is 1.5× or less. Cold passes if StarlingMonkey's maximum is under 250 ms. The snapshot rows decide the production verdict.

Pair StarlingMonkey with deno_core with snapshot on warm GET, warm POST and the slowest repeated Hono case, following the [spike's methodology](functions-wasm-spike.md#final-verdict). Measure cold after preparation. Report preparation separately, including an empty cache, so the HTTP cold limit cannot hide a cache-miss build. Check IPC/3, large request bodies, UTF-8 response bounds, multipart bytes, `Response.clone`, cancellation and shutdown before release.
