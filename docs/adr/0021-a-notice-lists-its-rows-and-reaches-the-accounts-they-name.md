# A notice lists its rows and reaches the accounts they name

Status: accepted, 2026-11-08. Amends [ADR-0016](0016-a-mutation-may-notify-the-owner-or-the-actor.md), which deferred sending to account IDs, and [ADR-0017](0017-the-kernel-runs-a-declared-schedule.md), whose scheduled notice had no row values.

Under ADR-0016 a notice template took `{input.<key>}` and `{actor.id}`, and `to` was `owner` or `actor`. A scheduled run has no input and no caller, so a nightly digest could only tell the owner "something is due, open the app" (capability matrix F17 and F18 in `docs/research/capability-matrix.md`). A team tool could not tell the assignee, and a reminder could not reach the person it reminds.

## Decision

Three additions to `notify`, all inside the mutation's declaration in `actions.json`:

- **`{kernel.now}`** fills with the time of the call or of the scheduled run, as `2026-11-08 07:00 UTC`: always UTC, to the minute. A scheduled run shows the same instant its `kernel.now` binding received. It may appear in the subject and the body.
- **`"changes": ["<column>", ...]`** names 1 to 8 columns of the changed rows. `{changes}`, in the body only, lists one line per changed row, `- ` and the columns' values joined by ` · `, at most 50 lines and then `- and <n> more`. Each value loses its line breaks and keeps 200 characters, as an input value does. `{changes.count}` fills with the number of rows the statement changed, in the subject or the body, and needs no list.
- **`"to": { "column": "<name>" }`** sends one notice to each account whose ID a changed row holds in that column. Each recipient's `{changes}` and `{changes.count}` cover only the rows that name that account.

**How the Kernel reads the rows.** When a notice lists rows or names a column, the Kernel appends its own `RETURNING [col], ...` to the statement before it runs it, in the same transaction, and reads back at most 1,000 rows. The author still may not write `RETURNING` (`mutation.returning`), and the answer stays `{ changes, lastInsertId }`, because the rows go only to the notice renderer: `run_mutation` returns them beside the answer as a separate field, never inside it. Columns are quoted in brackets, because SQLite reads an unknown double-quoted name as a string literal, and a misspelled column would then pass the check and list its own name. A trailing `;` and anything after it are cut before the clause is appended.

**Who may receive it.** A column value is an account ID, never an address. The Kernel looks it up in this Deployment's `identity.sqlite` among active accounts with `verified_at` set, the same rule as `to: actor`. A value that is an email address, the ID of an unverified or suspended account, or no account at all sends nothing and counts under Usage as `<action>: not-a-verified-account`. A row whose column is null or not text names nobody and is not counted. The app's statement and access rules decide who can write an ID into that column; the host adds no rule of its own beyond verification, so a member who can assign a chore to another member can make the app write to that member, within the budgets below.

**The cap.** One run writes to at most 50 accounts, taken in account ID order. Each account past the 50th sends nothing and counts as `<action>: recipient-cap`, so the owner sees how many were left out. ADR-0016's budgets still apply to every notice: 200 a day per app, 500 per creator, 50 a day per recipient from one app. A run that uses its whole cap spends 50 of the app's 200, so at most four such runs reach their full cap in a day; the rest stop at `app-limit`. Rows past the first 1,000 a statement changes are counted in `{changes.count}` for `owner` and `actor` but are not listed, and their accounts are not addressed.

**Both doors.** `parseNotify` in `src/kernel/actions.ts` and `notify::declaration` in `kernel-rs/src/notify.rs` check the declaration in the same order with the same words, from `kernel-rs/src/notify-cases.json`. Whether the columns belong to the changed table is checked against the schema: the Validation Gate prepares the statement with the Kernel's clause in sql.js, and the Kernel does the same in `release_plan` and at publish when it applies the schema, from `kernel-rs/src/notify-column-cases.json`. The notify probe checks that the Gate and `release_plan` give the same sentence. New refusals: `notify.changes-invalid`, `notify.changes-in-subject`, `notify.changes-undeclared` and `notify.column-unknown`. The sentences of `notify.invalid`, `notify.recipient-invalid` and `notify.placeholder-unknown` now name the new forms.

**Where it lives.** The declaration is in `actions.json` and the accounts are in `identity.sqlite`, so a package, a migration and an Eject carry both, and the imported app addresses the same members. `konae dev` now writes its email to `.konae/dev-data/mailbox.jsonl` and passes `KONAE_SCHEDULE_MIN_SECONDS` to its Kernel, so a person can watch a scheduled notice arrive on their own machine.

## Considered options

- **A second statement under `notify`, a query that names the recipients.** Rejected. A query run after the mutation cannot tell which rows the mutation changed unless the author writes a marker column and repeats its condition, and a DELETE leaves nothing to query. It doubles the SQL a person has to get right and opens a second read path that the action's bindings do not bound. `RETURNING` reports exactly the rows SQLite changed, in the same transaction, with no race. Its limits are SQLite's: it reports only the table the statement changes, not rows a trigger or a foreign key action changes, and Konae runs no triggers.
- **Let the author write `RETURNING`.** Rejected. Mutations answer `changes` and `lastInsertId` at both doors (`mutation.returning`), and a returned row would reach the caller. The Kernel's own clause keeps the rows out of the answer by construction.
- **`RETURNING *`.** Rejected. It would mail every column, including ones the app never shows, to whoever a row names. The author lists what the notice may show.
- **An address column.** Rejected for the reason ADR-0016 gives: an address read from a row is an address a visitor or member wrote, and the app becomes a relay.
- **No cap, or a cap that sends to whoever comes first.** Rejected. Without a cap one run of an UPDATE over a large table could spend every notice budget at once. Order by account ID makes the cut repeatable, so the owner can reason about who was left out; it also means the same accounts are left out on every capped run, which the owner reads under `recipient-cap`.
- **A per-recipient unsubscribe.** Deferred. Verification proves an address belongs to an account of this app; it does not record consent to every notice. The per-recipient budget of 50 a day bounds the harm until an unsubscribe exists.

## Consequences

A nightly digest can say what is due and send each person their own part: the digest template now stamps yesterday's entries and mails each author a list of what they wrote. A team tool can tell an assignee, a reminder reaches the person it names, and a scheduled run that changes nobody's rows sends nothing. `{changes}` is limited to columns of the changed table, so a notice that wants a value from another table needs the statement to copy it into a column of the changed table first. The editor preview still sends no email; `konae dev` and a Deployment do. `examples/probes/notify-rows/replay.ts` runs a scheduled reminder on `konae dev` and checks the mailbox: one notice to each of two invited members, each listing only their own chores, and nothing to an email address or an unknown ID written in a row.
