# Hardening del runner de funciones

Las pruebas Linux corrieron en Docker ARM64 sobre Linux 7.0.14. Rust fue 1.91.1. El runner usa `deno_core` 0.413.0, `deno_web` 0.291.0, `deno_webidl` 0.260.0, `deno_fetch` 0.284.0 y `deno_net` 0.252.0, fijados en `rust-host/Cargo.lock`. Se compiló con Cargo bloqueado y offline contra el archivo oficial V8 `librusty_v8_simdutf_release_aarch64-unknown-linux-gnu.a.gz`. La compilación reutilizó el volumen Cargo `konae-functions-hardening-linux-target-20261120` y sus fuentes descargadas. No se cambió ni se limpió la caché global de Docker.

## Resultados por criterio

- **A, runner y empaquetado.** El runner ARM64 `df1d3de9b6cbab0d41a28d23e1df810be735b9fe7a24716892619703a638330b` pasó `clean-smoke-bootstrap-r2.log` en Python 3.12-slim. El contenedor recibió solo el ejecutable y el smoke devolvió Ready, HTTP 200 y ShutdownComplete sin checkout, Cargo ni registro. Las imágenes ARM64 finales tienen ID `sha256:e2f2f17582a6f4308c76b0c8b4eb9c802b4f8863e8f834c380fbc3dd9f5dde56` y `sha256:14bc714d91c8e4cdaf9e3f961640adb7a9b15e026891d072a52af3e06c31a625`. Konae AMD64 final tiene ID `sha256:dc15c4792f16900869c7de28671cefca9389259b33e6e3f3565d9599ede8b779`. `scripts/build-functions-images.sh` detecta la arquitectura ELF y entrega el runner como contexto BuildKit. `Dockerfile.konae` verifica cabecera y arquitectura ELF después de compilar y empaquetar. Los intentos antiguos `dockerfile-kernel-build-r1.log` y `dockerfile-kernel-build-final-r1.log` conservan el fallo histórico de metadatos BuildKit.
- **B, aislamiento Linux.** `strict-oom-bootstrap-r3.log` comprueba que el hijo ejecuta como UID/GID separados, con CapEff vacío, entorno limpio, descriptores heredados cerrados, Landlock ABI 5 y seccomp. Un fixture nativo no abrió `/etc/passwd`, `/proc/self/environ` ni controles cgroup; tampoco creó sockets de red ni señalizó al supervisor. `sandbox-refusal-linux-final-r1.log` ejecuta el runner empaquetado bajo un perfil que deniega `landlock_create_ruleset`; el worker responde `sandbox_unavailable` y termina antes de recibir código. La prueba unitaria `kernel-macos-sandbox-refusal-test-r2.log` fija el mapeo de ese código a HTTP 503 y su mensaje. En las imágenes, `kernel-image-strict-entrypoint-function-final-r7.log` y `konae-image-strict-entrypoint-final-r5.log` muestran ambos entrypoints vivos con CapEff `0xe0`, solo `CAP_KILL`, `CAP_SETUID` y `CAP_SETGID`. La configuración de prueba dejó `cgroup.procs` escribible por el Kernel UID 10001 y mantuvo `cgroup.subtree_control` y `memory.max` bajo UID 0. La imagen Kernel sirvió una función autenticada desde SQLite. El hijo se adjunta al cgroup antes de cambiar de UID; espera un marcador privado y no recibe el bundle hasta que descarta capacidades y aplica Landlock/seccomp.
- **C, OOM.** La prueba estricta del runner final distingue un SIGKILL ordinario, `worker_failed` con delta OOM 0, de un OOM real del cgroup, `worker_memory_limit` con delta 4. El helper recibió SIGKILL; el worker se recogió y su subgrupo se retiró. El binario `oom-probe` probado tiene SHA-256 `39600142a3eaca7fa0b8f95518bec7997d61cfffc64ac2eeaf10d99855ed65af`.
- **D, ciclo de vida.** El mismo log confirma que `pids.max=64` detuvo los forks con `pids.current=64`. SIGKILL al supervisor mató y recogió al worker por `PDEATHSIG`. El siguiente arranque quitó el subgrupo huérfano por PID y tiempo de inicio; un grupo hermano quedó intacto. La prueba de imagen también reinició Kernel y verificó la limpieza del subgrupo anterior.
- **E, Kernel y función integrada.** `kernel-http-final-bootstrap-strict-r1.log` pasó auth de dos actores, aislamiento de filas SQLite, transacciones, rollback, idempotencia, publicación concurrente, timeout, OOM y respuesta 200 tras recuperación. El binario de prueba tenía SHA-256 `0629dcc906326d544db23db078d2e48b365cd09906344d3697dedce3f10b20e5`. Tres rondas pequeñas registraron fríos de 37,84, 39,20 y 36,64 ms, y calientes de 1,50 a 2,17 ms. Son muestras ARM64 de ese recorrido, no una comparación ni una medida de producción. `kernel-image-strict-entrypoint-function-final-r7.log` ejecutó el entrypoint real de la imagen final con una app publicada, una sesión restaurada y la fila `quantity=6`; la llamada autenticada respondió HTTP 200. Los entrypoints de ambas imágenes rechazaron la falta de `KONAE_FUNCTIONS_CGROUP` con un mensaje claro. Siguen vigentes las pruebas separadas `kernel-export-import-strict-linux-final-r1.log`, `kernel-unknown-strict-linux-r1.log` y `kernel-module-off-strict-linux-r1.log` para traslado, resultado incierto y módulo apagado sin spawn.
- **F, documentación y estado.** ADR-0018 y `docs/operate.md` indican el empaquetado, el modo Linux estricto, los requisitos de operador y el límite de macOS. La adopción continúa experimental. Los contenedores de prueba tenían límites de memoria y procesos, namespace cgroup privado y red desactivada. Un helper usó capacidades de montaje y propiedad durante la preparación y las retiró antes del entrypoint. Esa preparación no configura por sí sola un despliegue normal.

## Requisitos del operador

El operador debe usar namespaces cgroup y PID privados, montar cgroup v2 y habilitar `memory` y `pids` antes del arranque. El namespace cgroup contiene solo la delegación de esa instalación. El namespace PID limita el alcance de `CAP_KILL`. `KONAE_FUNCTIONS_CGROUP` apunta al directorio raíz dedicado. El Kernel UID necesita crear y retirar grupos bajo ese directorio y escribir `cgroup.procs` en la raíz delegada y en su propio grupo de origen. El operador conserva la propiedad de `cgroup.subtree_control` y de los límites de la raíz. El Kernel no necesita `CAP_SYS_ADMIN`; la prueba final confirmó que el Kernel UID no puede escribir `cgroup.subtree_control`.

El entrypoint elige como identidad del Kernel el propietario de la primera carpeta de app. `KONAE_FUNCTIONS_UID` y `KONAE_FUNCTIONS_GID` deben ser distintos. El runtime debe conceder `CAP_KILL`, `CAP_SETUID` y `CAP_SETGID`, mantener Landlock ABI 5 o posterior y seccomp, y permitir que el worker corra con capacidades vacías. El operador debe probar estas condiciones en su runtime y sistema de archivos. El contenedor Linux de prueba no prueba automáticamente otra plataforma de despliegue.

`KONAE_FUNCTIONS_RUNNER` queda sin configurar por defecto. Para construir imágenes, el operador prepara un directorio con el ejecutable `konae-functions-spike` para la arquitectura destino y ejecuta `scripts/build-functions-images.sh <runner-bundle-dir> <tag-prefix>`. El build copia el binario exacto de ese directorio. En el arranque no hacen falta Cargo, el registro Cargo ni fuentes de build.

`KONAE_FUNCTIONS_DEVELOPMENT=1` usa sondeo RSS y omite el aislamiento Linux. macOS se conserva como entorno de desarrollo y no tiene una barrera equivalente. Ninguno de esos modos constituye una frontera de producción.

## Evidencia y reproducción

El checkpoint r2 y los informes r3 preservan los estados anteriores, incluidos los fallos de BuildKit y la discrepancia del runner. No se publicaron las imágenes incorrectas. Los recorridos HTTP no se repitieron en esta ronda porque sus fuentes y artefactos ARM64 no cambiaron.

`image-kernel-sandbox-denial-r4.log` demuestra el 503 y que SQLite no recibió mutaciones; `image-konae-auth-sql-r3.log` demuestra auth y lectura SQL en el entrypoint Konae. `release-konae-amd64-r4.log` documenta que una capa cacheada contenía un ejecutable Konae con cabecera ELF nula pese a que la imagen indicaba linux/amd64. `release-konae-amd64-r5.log` registra el rebuild con retirada del binario previo, comprobación ELF por arquitectura y comprobación posterior al empaquetado. La imagen resultante contiene Konae x86-64 SHA-256 `7e3c118a0c3a5239f1650c0c974f69e683a945ac9748ec084b199c7ce953f69f` y el runner AMD64 esperado SHA-256 `1014c7a522dc260cab132cf52336626e5a03407baab1103fb59ea913c9b6e48c`. `konae-amd64-missing-delegation-r5.log` registra el rechazo del entrypoint con exit 1 cuando falta `KONAE_FUNCTIONS_CGROUP`.

El contrato del workflow se revisó localmente: descarga el tar del runner por arquitectura, calcula su SHA, lo entrega como contexto BuildKit y pasa el hash como build arg. No se ejecutó GitHub Actions ni se hizo push. Las dos imágenes ARM64, Kernel AMD64 y Konae AMD64 compilaron localmente en rondas registradas. El executor no depende de systemd. El laboratorio preparó directamente un subárbol cgroup v2 y ejercitó la delegación y el aislamiento que consume el Kernel. Sigue pendiente verificar que el service manager y runtime elegidos en un despliegue real apliquen el contrato documentado; esa validación no es un requisito de systemd para el código.

`sources-amd64-konae-r5.sha256` fija después de la prueba los archivos de código, manifiestos y Dockerfiles relevantes; la misma ronda no modificó esos archivos mientras BuildKit compilaba. No se guardó una segunda copia criptográfica previa al inicio, así que el registro es una huella posterior y no un manifiesto before/after independiente. `artifacts-amd64-konae-r5.txt` fija el digest de imagen y los hashes del ejecutable y runner inspeccionados dentro de ella.

La ronda recuperó espacio eliminando únicamente `kernel-rs/target/debug/incremental`, caché regenerable que ocupaba 5,4 GiB y no estaba abierta por procesos. Se mantuvieron los binarios, `deps`, `release`, el código y la evidencia. Antes del build se confirmó escritura del daemon con un contenedor `/bin/true` descartable. Se borraron tres tags duplicados o inválidos creados por esta tarea, sin prune global; se preservaron las imágenes ARM64 finales y Kernel AMD64. El contexto de build excluye `**/node_modules/` para omitir dependencias anidadas ajenas a la imagen. Al terminar, se retiró el directorio temporal propio del runner AMD64 y se comprobó que no quedaran contenedores. El margen observado fue 18 GiB libres.
