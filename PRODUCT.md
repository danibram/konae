# Konae product

## Register

product

## Users

An owner makes and manages small apps. A person who does not write code describes an app and sees it run. A person who writes code edits the same app's files. Both need to understand the checks, who can open the app, which rows are live and what an export carries.

## Product purpose

Konae lets both people make the same small app and take it to another machine with its accounts, its data and its rules unchanged. AGENTS.md defines the five jobs. CONTEXT.md defines the product's words.

## Brand personality

Calm, direct and legible. The editor shows the app and the next useful action. It states what happened and what the owner can do. Interface copy stays in English.

## Anti-references

Avoid repeated explanations, competing primary actions, technical setup in everyday app management and notices that disagree about access or publication. Do not use decorative shadows inside panels or monospace for ordinary labels and help text.

## Design principles

- Show the same publication state on the project card, in the editor and in Deploy. Compare saved sources with the release rather than browser history.
- Keep Describe beside Preview when the screen has room. Keep a visible route back to Projects and a switcher that names the current app.
- Distinguish preview test rows from the published app's rows. State which rows a view changes.
- Put accounts, access and portability within reach using the product's existing declarations and tools.
- Use the shared components and tokens described in docs/design-system.md. Keep one primary action for the current task.

## Accessibility and inclusion

The theme follows the system. Text needs at least 4.5:1 contrast in light and dark. Controls need visible keyboard focus, accessible names and predictable tab order. Dialogs return focus to their opener. Layouts must work at phone widths and between desktop breakpoints. Respect reduced motion and keep short loading operations from flashing a fallback.
